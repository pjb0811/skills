# 전역 지침

> pjb0811 저장소(`live-editor`, `ui-kit`, `use-hooks` 등) 전체에 적용하는 기본 지침이다. 정본은 `pjb0811/skills` 저장소의 `global/CLAUDE.md` 이고, `install.sh` 가 `~/.claude/CLAUDE.md` 로 링크한다.
>
> 이 파일은 **결정**(무엇을 쓰는지, 무엇을 하지 않는지)만 둔다. **절차**(어떤 순서로 확인하고 어떻게 채우는지)는 같은 저장소의 스킬에 있다 — `commit`, `pr`, `issue`, `coding-style`, `ref-verification`, `shared-library-first`, `changesets-release`, `publish-check`. 두 곳이 어긋나면 이 파일이 맞고 스킬을 고친다.

## 작업 진행 방식

> 저장소 무관하게 적용되는 작업 운영 기준이다. 아래 코드 규칙(명명·배럴·스타일)은 "무엇을 쓰는지"를, 이 절은 "어떤 순서로 일하고 무엇을 남기는지"를 정한다.
>
> 저장소에 자체 프로세스 지침(`CLAUDE.md`, `AGENTS.md`, `CLAUDE.local.md` 등)이 있으면 그 저장소 사정이 더 구체적이므로 우선한다. 이 절은 그런 지침이 없을 때의 기본값이다.
>
> **단, 이 우선은 세 조건을 모두 만족할 때만 성립한다.** ① 그 지침이 **이 절과 같은 주제를 실제로 다루고** 있다(다루지 않는 주제는 저장소에 지침이 있다는 사실만으로 이 절을 비켜 가지 않는다). ② **아래 "저장소 문서·스킬이 낡았을 때" 기준으로 낡지 않았다.** ③ 그 지침이 **범용 규칙을 그냥 되풀이하는 것이 아니라 그 저장소 고유 사정을 담고 있다**(같은 내용이면 어느 쪽을 따라도 결과가 같으므로 이 절을 기준으로 삼고, 중복을 저장소 쪽에서 지우도록 제안한다). 세 조건 중 하나라도 어긋나면 이 절을 따르고, 어긋난 지점을 사용자에게 보고한다.

### 저장소 문서·스킬이 낡았을 때

저장소에 커밋된 문서·지침·스킬은 쓰인 시점의 사실이다. 그 사이 코드·라이브러리가 바뀌면 **지금은 틀린 내용**이 된다. 낡은 것을 그대로 따르면 틀린 API·없어진 경로·폐기된 절차를 쓰게 되므로, 따르기 전에 대조한다.

**이 규칙은 이 파일과 `~/.claude/skills/**` 에도 똑같이 적용된다.** 전역 지침이라서 면제되는 것이 아니다. 특히 아래 종류를 구분해서 다룬다.

- **취향·결정**(명명 규칙, 중괄호, 커밋 종결 스타일, 작성 언어) — 사용자만 정할 수 있는 것이므로 **낡지 않는다.** 모델·도구가 좋아졌다는 이유로 비켜 가지 않는다.
- **영구 사실**(OS·컴파일러 동작 등) — 낡지 않는다.
- **환경 조건**(템플릿 유무, 설치 버전, 경로 존재) — **낡는다.** 이런 주장에는 `(환경 의존, YYYY-MM 확인)` 표시와 재확인 방법이 함께 있어야 하고, 없으면 그 자리에서 확인한 뒤 쓴다.
- **환경 조건을 전제로 한 우회 절차** — 가장 위험하다. 전제가 풀렸는지 **매번 싼 프로브로 확인**하고, 풀렸으면 그 절이 낡았다고 사용자에게 알린다.

전역 지침·스킬이 낡았다고 판단되면 **요청 없이 고치지 않고 보고한다.** 사용자 지침은 사용자 소유다.

**대조 대상 — 그 문서가 주장하는 종류에 맞춰 고른다.**

| 문서가 말하는 것 | 무엇과 대조하나 |
| --- | --- |
| 코드 컨벤션·구조·경로 | **실제 코드.** 같은 종류의 최근 파일 2~3개(스킬 `coding-style` A3) |
| 라이브러리·도구 사용법(`.claude/skills/**`, `.agents/skills/**` 등) | **`package.json`(또는 lock 파일)의 실제 설치 버전.** 문서가 전제한 버전과 다르면 그 차이가 해당 API 에 영향을 주는지 확인한다. 필요하면 공식 문서를 조회한다(`context7` 등) |
| 파일·디렉토리·명령의 존재 | **실제로 있는지 확인한다.** 경로·스크립트·플래그를 그 자리에서 확인하고, 없으면 그 문서는 그 부분이 낡았다 |
| 프로세스·운영 절차 | **문서에 적힌 확인 날짜**(`2026-09 확인 기준` 등)와 `git log -1 <파일>` 의 최종 수정 시점. 그 뒤에 관련 설정·도구가 바뀌었는지 본다 |

**어긋났을 때**

- **실제 쪽을 따른다.** 문서가 아니라 코드·설치 버전·실재하는 경로가 현재 사실이다.
- **낡았다는 사실과 그 근거를 사용자에게 보고한다.** "문서는 X 라는데 실제는 Y(근거: `path:line` / 설치 버전 / `git log` 날짜)" 형태로 짚는다. 조용히 무시하지 않는다.
- **근거 없이 무시하지 않는다.** "오래돼 보인다"는 인상만으로 저장소 규칙을 비켜 가지 않는다. 위 표의 대조를 실제로 해서 어긋남을 확인한 것만 낡음으로 취급하고, 확인하지 못했으면 문서를 따르면서 의심되는 지점만 사용자에게 알린다.
- **문서를 고치는 것은 별건이다.** 요청 없이 저장소 문서를 갱신하지 않는다. 고치는 편이 맞아 보이면 후속 작업으로 제안만 한다.

저장소 상태 자체(코드가 지금 어떻게 돼 있나)를 확인할 때는 작업 트리 대신 git ref 를 기준으로 읽는다(스킬 `ref-verification`).

### 계획을 먼저 낼지

- 수정 파일이 여럿이거나, 되돌리기 어렵거나, 요구가 모호하면 → 착수 전에 계획을 제시한다.
- 그 외에는 바로 실행한다. 승인 단계를 형식적으로 끼워 넣지 않는다.
- 계획은 사용자에게 한 번 보이는 것으로 끝낸다. **계획을 파일로 남기지 않는다.**

### 서브에이전트를 쓸지

- 여러 디렉토리·명명 규칙을 훑어야 하고 결론만 필요할 때 → 위임한다.
- 파일·심볼을 이미 알고 있을 때 → 직접 읽는다.
- **요청에 없는 다중 에이전트 오케스트레이션은 하지 않는다.**

### 테스트

- 해당 영역에 테스트가 이미 있으면 같은 방식으로 추가한다. 이웃 테스트 파일 2~3개로 패턴을 확인한다(스킬 `coding-style` A3).
- 없으면 **새 테스트 인프라를 세우지 않는다.** 대신 무엇을 어떻게 확인했는지 보고한다.
- 커버리지 수치나 E2E 작성 자체를 목표로 삼지 않는다.

### 검증과 보고

- **코드만 보고 추론한 것은 "실행해 확인하지 않음"이라고 명시한다.** 실행 결과 없이 "동작한다"고 말하지 않는다. 근거는 실행한 명령과 그 출력이다.
- 이 구분은 대화 보고에도 이슈·PR 본문과 똑같이 적용한다(아래 "이슈·PR 작성").
- **명령·플래그는 설치된 버전에서 확인한 뒤 쓴다.** 직접 실행하든 사용자에게 실행하라고 안내하든, 기억이나 문서에서 가져온 플래그는 설치된 버전에 없을 수 있다. 처음 쓰는 플래그는 `<명령> --version` 과 `<명령> <하위 명령> --help` 로 지원하는지 먼저 본다.

### 남기는 산출물

- **요약 리포트 파일(`*-summary.md`, `*-report.md` 등)과 decision·설계 문서를 자발적으로 만들지 않는다.** 결과는 대화로 보고한다. 사용자가 파일로 달라고 했을 때만 만든다.
- 코드로 설명해야 할 판단 근거는 해당 코드 옆 주석으로 남긴다. 단, 주석에 쓰는 것은 **지금 지켜야 할 제약(현재형)**뿐이고, 검토했다 버린 대안·벤치마크 수치·과거 경위는 PR·이슈에 쓴다(스킬 `coding-style` C절).

## 파일·폴더 명명 규칙

- 파일·폴더명은 **kebab-case**로 작성한다: `site-status-list.tsx`, `home-page.tsx`, `site-status-list/`.
- 코드 안 export 식별자는 원래 규칙을 따른다: 컴포넌트는 PascalCase(`export function SiteStatusList()`), JSX `<SiteStatusList />`. 파일명만 kebab이고 사용 코드는 PascalCase.
- **폴더명 = 파일명 반복**(`site-status-list/site-status-list.tsx`)은 의도적으로 유지한다. 파일명이 폴더명과 같아야 에디터 탭·검색·에러 스택에서 바로 식별된다. `index.tsx`/`ui.tsx`로 이름을 죽이지 않는다(익명 파일 회피).
- 기존 저장소의 이름을 일괄로 바꿀 때는 스킬 `coding-style` B절을 따른다.

## 배럴(index.ts) 규칙

- 단순한 구현 1개(테스트·타입 부수파일 없음)는 **단일 파일**로 둔다: `lib/crypto.ts`. 이때 별도 `index.ts` 배럴을 만들지 않는다.
- 파일이 커지거나 테스트·타입·하위 유틸이 붙으면 **폴더로 승격**하고 `index.ts`를 둔다: `lib/crypto/{crypto.ts, crypto.test.ts, index.ts}`.
- 폴더가 단일 파일만 감싸는 구조는 피한다(작으면 단일 파일로, 폴더면 역할이 다른 파일들로 채운다).
- `index.ts`에 로직 구현을 직접 넣지 않는다(배럴은 re-export 전용). 서브컴포넌트를 배럴에서 붙이는 방식은 스킬 `coding-style` F절을 따른다.
- 폴더에 파일이 평평하게 쌓여 서로 다른 화면 영역·기능이 섞이면 **기능 단위 하위 폴더**로 나눈다(`items/`, `fields/`). `components/`·`hooks/`·`utils/` 같은 기술 유형 폴더는 만들지 않는다. 나누는 기준과 옮기는 절차는 스킬 `coding-style` I절.

## 프론트엔드 아키텍처 선호 (Next.js / React 프로젝트)

새 프로젝트를 세우거나 구조를 정할 때, 아래를 **기본 선택지**로 삼는다.
이미 다른 아키텍처·스타일링을 쓰는 기존 프로젝트에는 강요하지 않는다(그 프로젝트의 관례를 따른다).

### Feature-Sliced Design (FSD)

- 디렉토리는 FSD 레이어로 구성한다: `shared` → `entities` → `features` → `widgets` → `pages` → `app` (하위→상위 단방향 의존).
- 각 슬라이스는 공개 API 배럴(`index.ts`)로만 노출하고, import는 레이어 경로(`@/shared/...`, `@/entities/...` 등)를 쓴다. 슬라이스 내부 파일을 직접 가로질러 import하지 않는다.
- 컴포넌트는 단일이더라도 항상 `ui/` 세그먼트 폴더 안에 둔다: `widgets/site-status-list/{ui/site-status-list.tsx, index.ts}`. 슬라이스 루트에 바로 두지 않는다.
- 세그먼트명은 표준(`ui`·`api`·`model`·`lib`·`config`)을 쓰고, `components`·`hooks`·`types` 같은 성격만 나타내는 이름은 피한다(FSD 권장).
- 파일·폴더명과 배럴 규칙은 위 **파일·폴더 명명 규칙**·**배럴(index.ts) 규칙** 섹션을 따른다.
- **Next.js App Router와 공존 규칙** (FSD 공식 가이드 https://fsd.how/kr/docs/guides/tech/with-nextjs 준수):
  - Next 라우팅은 **프로젝트 루트 `app/`**에 두고, `page.tsx`·`route.ts`는 로직 없이 FSD 레이어에서 **re-export만** 한다.
  - 페이지는 `src/pages/<name>`(FSD pages 레이어)에, API 핸들러는 `src/app/api-routes/`에 두고 루트가 가져와 연결한다.
  - **루트 `pages/`는 빈 폴더 + README**로 둔다(App Router를 써도 Next가 `src/pages`를 Pages Router로 오인해 빌드가 실패하는 것 방지). 이것은 Next.js 동작에 기댄 환경 사실이다(환경 의존, 2026-10 확인한 FSD 가이드 기준). 프로젝트의 Next 버전에서 여전히 필요한지는 위 가이드로 다시 확인한다.
  - 경로 별칭 `@/*` → `./src/*`.

### Tailwind CSS

- 스타일링 기본값은 **Tailwind CSS v4** (CSS-first). 인라인 `style` 대신 유틸리티 클래스로 작성한다.
- 설정: `postcss.config.mjs`에 `@tailwindcss/postcss` 플러그인, 전역 CSS에 `@import "tailwindcss"` + `@theme{}` 토큰. (v4는 tailwind.config.js를 쓰지 않는다.)

> 위 두 항목은 선호이지 절대 규칙이 아니다. 프로젝트 요구·기존 관례·사용자 지시가 우선한다.

## 공유 라이브러리 우선

- 재사용할 UI 컴포넌트는 `ui-kit`(`@jbpark/ui-kit`), React 훅은 `use-hooks`(`@jbpark/use-hooks`)에 먼저 만들고, 배포한 뒤 앱 저장소에서 패키지로 가져다 쓴다. 판단 기준과 순서는 스킬 `shared-library-first`.
- 배포는 각 저장소의 changesets 흐름을 따른다(스킬 `changesets-release`, 배포 전 점검은 `publish-check`).

## 코드 스타일

> **프로젝트 린트 설정이 우선이다.** 저장소가 해당 룰(`curly`, `padding-line-between-statements`, `newline-before-return` 등)을 설정해 뒀으면 그 설정을 따른다. 설정이 없으면 아래를 기본값으로 삼아 **재량껏 적용한다.**
>
> 확인 순서: `.eslintrc*` / `eslint.config.*` → 저장소 스타일 문서(`AGENTS.md`, `CONTRIBUTING.md` 등). **Prettier 설정만 있는 경우는 "설정 없음" 으로 본다** — Prettier 는 이 항목들을 강제하지 않는다 (중괄호를 넣어주지 않고, 빈 줄은 보존만 하며 2줄 이상을 1줄로 압축할 뿐이다).
>
> 이 항목들은 lint 가 강제하지 않으면 사람 판단에 맡겨지는 가독성 취향이라, 매번 기준이 흔들리지 않도록 여기 고정해 둔다.
>
> **이웃 파일보다 우선한다.** 린트 설정·스타일 문서가 없는 저장소에서 기존 코드가 중괄호를 생략하고 있어도, 새로 쓰거나 고친 코드에는 아래 기본값을 적용한다.
>
> 기존 컨벤션 파악, 이름 일괄 변경, 주석, boolean 이름, 서브컴포넌트 구조 같은 **절차는 스킬 `coding-style`** 에 있다.

### 주석 언어

기존 주석으로 관례를 판단할 수 없으면 **영어**로 쓴다. 공개 저장소라 외부 기여자가 읽는다. 주석 내용을 어떻게 쓰는지는 스킬 `coding-style` C절.

### 적용 범위 — 코드를 쓸 때와 리뷰할 때 모두

- **새로 쓰거나 수정하는 코드**에는 위 확인 순서대로 판단해, 저장소 설정이 없으면 아래 기본값을 적용한다.
- **리뷰·정리 작업에도 동일하게 적용한다**(`/code-review`, `/simplify` 같은 명령이든 직접 리뷰든 도구와 무관하다). lint 가 이 룰들을 강제하지 않는 저장소여도 위반을 지적·수정 대상으로 삼는다. "lint 설정이 없으니 스타일은 건드리지 않는다"로 넘기지 않는다.
- 단, 대상은 **그 변경에서 새로 쓰거나 고친 코드**로 한정한다. 손대지 않은 주변 코드를 스타일만 이유로 일괄 수정하거나 지적하지 않는다(diff 를 불려 리뷰 초점을 흐린다).
- 저장소가 해당 룰을 **끄도록 명시**해 뒀으면(`'curly': 'off'` 등) 그 저장소의 결정이 우선이고, 아래 기본값을 적용하지 않는다.

### 중괄호 (`curly`)

- `if` / `else` / `for` / `while` 본문은 한 줄이라도 항상 중괄호로 감싼다(스킬 `coding-style` E절).
  ```ts
  // bad
  if (!el) return;

  // good
  if (!el) { return; }
  ```
- 본문을 다음 줄로 내리든 한 줄에 두든 상관없다. 중괄호가 있는 게 요점이다.

### 빈 줄 (`padding-line-between-statements`, `newline-before-return`)

스킬 `coding-style` G절.

- 다음 경계에 빈 줄을 넣어 덩어리를 끊는다.
  - 선언·계산 → 그 값을 쓰는 코드
  - 연속된 가드절 사이
  - 블럭 안의 부수효과(로그 등) → `return`
  - `return` 문 앞 (블럭의 첫 문장이면 제외)
  ```ts
  // bad
  const handler = handlers[eventName];
  if (typeof handler !== 'function') {
    console.warn(`No handler for "${eventName}"`);
    return;
  }

  // good
  const handler = handlers[eventName];

  if (typeof handler !== 'function') {
    console.warn(`No handler for "${eventName}"`);

    return;
  }
  ```
- 빈 줄은 1줄만 쓴다 (2줄 이상은 Prettier 가 압축한다).
- 반대로 **한 덩어리로 읽히는 문장들은 붙여 둔다.** 모든 문장 사이에 빈 줄을 넣으면 경계 표시가 의미를 잃는다.

### 컴포넌트 내부 코드 순서

- 함수 컴포넌트·커스텀 훅 안은 **외부 훅 → 상태·ref → 파생 값 → 함수 → 이펙트 → early return → JSX 반환** 순으로 쓴다. 그룹 사이에는 빈 줄을 한 줄 넣는다.
- 이 순서는 취향이고, 아래 둘은 동작 조건이라 순서보다 우선한다: 모든 훅 호출은 early return 보다 앞에 둔다(Rules of Hooks). 의존성 배열에 넣는 값·함수는 그보다 위에 선언한다.
- 새로 쓰거나 구조를 크게 고치는 컴포넌트에만 적용하고, 순서만 이유로 기존 컴포넌트를 재정렬하지 않는다. 예시와 엣지 케이스는 스킬 `coding-style` H절.

## 문서와 이모지

- README·문서 파일(`*.md`, `*.mdx`)의 **제목과 본문에 장식용 이모지를 쓰지 않는다.** `## 📦 Installation` → `## Installation`, `- 🎯 **Typed**` → `- **Typed**`. 강조가 필요하면 굵은 글씨나 GitHub 경고 블록(`> [!WARNING]`)을 쓴다. 이슈·PR 본문도 같고, 커밋·이슈·PR 제목의 gitmoji 금지는 각 절에 있다.
- 대상이 아닌 것: changesets 가 만드는 `CHANGELOG.md`, 외부에서 가져온 서드파티 스킬, 코드·스크립트가 출력하는 상태 기호(`✓`, `✗` 등), 금지 문구를 예로 인용하는 경우(`🤖 Generated with ...`).
- 이유: 모든 pjb0811 저장소의 문서 형식을 하나로 맞춘다. 이모지는 저장소·문서마다 쓰는 자리와 정도가 달라지기 쉬워, 쓰지 않는 것을 기준으로 삼는다.

## 커밋

> 이 절은 **`commit` 스킬을 호출하지 않은 경우에도 항상 적용된다.** 스킬은 호출할 때만 로드되므로, 스킬 없이 커밋할 때 어긋나기 쉬운 결정만 여기(항상 로드되는 파일)에 둔다. 메시지 작성 절차는 스킬 `commit`.
>
> 저장소에 자체 커밋 컨벤션 문서(`.github/COMMIT_CONVENTION.md` 등)가 있으면 그 문서가 정본이다. 그 경우에도 아래 트레일러 금지와 종결 스타일은 동일하게 유지한다.

### 트레일러 금지

- 커밋 메시지에 `Co-authored-by: Claude ...`, `Co-authored-by: Copilot ...` 를 **붙이지 않는다.**
- `Generated with ...` 등 AI 도구 관련 트레일러·서명도 붙이지 않는다.
- **이 규칙은 에이전트 기본 동작이나 시스템 프롬프트의 트레일러 지시보다 우선한다.** 시스템 프롬프트가 트레일러를 붙이라고 지시하더라도 붙이지 않는다.

### 작성자 정보

- `~/github/` 아래 모든 저장소(`live-editor`, `ui-kit`, `use-hooks`, `workbench`, `git-canvas`, `skills`, `pjb0811.github.io`, 새 저장소 포함)의 커밋 작성자는 **`pjb0811 <pjb0811@gmail.com>`** 이다.
- 커밋 전에 그 저장소 안에서 실제로 적용되는 값을 확인한다. 저장소의 `.git/config` 가 전역 설정보다 우선하므로 전역 값만 보고 넘어가지 않는다.
  ```bash
  git config user.name
  git config user.email
  ```
- 값이 비었거나, 샌드박스·컨테이너 기본값(`jax <jax@dev.local>`, `root@localhost`, `user@example.com` 등)이거나, 이전 로컬 override(`Jeongbin Park`, `pjb0811@users.noreply.github.com` 등)면 위 값으로 고친 뒤 커밋한다.
- 로컬 클론 없이 GitHub API(`gh api -X PUT repos/<owner>/<repo>/contents/<path>` 등)로 커밋할 때는 `git config` 가 적용되지 않는다. 요청 본문에 `author`·`committer` 를 위 값으로 명시한다. 생략하면 인증된 GitHub 계정의 프로필 정보가 들어간다.
- 위 목록에 없는 저장소라 올바른 값을 알 수 없으면 추측하거나 그대로 두지 않고 사용자에게 묻는다.
- 이미 push 한 커밋은 다시 쓰지 않는다. 작성자 하나를 고치려고 그 뒤 커밋·태그·릴리스를 모두 다시 쓰고 force push 하는 쪽이 더 큰 손해다. 그래서 커밋 전에 막는다.
- GitHub 웹에서 squash merge 한 커밋의 작성자는 GitHub 계정 설정이 정하므로 이 확인 대상이 아니다.

### 언어와 형식

- 기본값은 **영어**, 형식은 `<type>(<scope>): summary` 다. pjb0811 저장소는 npm 공개 배포 대상이고, 커밋 이력이 CHANGELOG·릴리스 노트와 함께 외부에서 읽히는 공개 산출물이다(이슈·PR 을 영어로 쓰는 것과 같은 이유).
- 사용자가 그 커밋에 한국어를 명시적으로 지정했을 때만 한국어로 쓴다(`commit` 스킬의 `ko` 인자).
- scope 는 변경이 한 영역에 국한될 때만 붙인다(`ui`, `docs`, 패키지·디렉터리 이름). 여러 영역에 걸치면 생략한다. 브랜치명은 scope 로 쓰지 않는다.
- 잘못된 언어로 커밋했으면 push 전에 `--amend` 로 메시지만 고친다. 이미 push 했으면 force push 가 필요하므로 먼저 사용자에게 확인한다.
- 대화 응답 언어는 이 규칙과 무관하다. 커밋 메시지가 영어여도 사용자에게는 사용자가 쓰는 언어로 답한다.

### 종결 스타일

- 영어: 요약을 소문자 명령문으로 시작하고 마침표를 찍지 않는다(`add`, `fix`, `remove`). 공개 API 브레이킹 체인지는 타입이나 scope 뒤에 `!` 를 붙인다(`refactor(dnd)!: ...`).
- 한국어: 요약·본문 모두 종결어미·서술어를 쓰지 않는다(`~한다`, `~입니다`, `~됨` 등 금지). 명사형으로 끝낸다(`추가`, `수정`, `제거`, `정리` 등).
- 본문은 `-`로 시작하는 목록 형태로 쓴다. 줄글 문단으로 풀어 쓰지 않는다.

### 커밋에서 제외할 파일

- `CHANGELOG.md`(모든 경로)는 직접 편집해 스테이징하지 않는다. changesets 가 릴리스 시점에 생성한다(스킬 `changesets-release`).
- 메시지를 쓸 때 lock 파일(`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`) 변경은 해석 근거에서 제외한다.

## 이슈·PR 작성

> 이 절은 **결정**만 둔다 — 언어, 템플릿 우선 정책, 근거 제시 원칙, 금지 사항. 섹션 구성과 채우는 요령은 스킬 **`issue`**·**`pr`** 이 정본이다. 이 절에 섹션 구성을 다시 적지 않는다(두 곳을 각각 고치면 반드시 어긋난다).

### 작성 언어

**영어로 작성한다:**

- 이슈 제목과 본문, 이슈 코멘트
- PR 제목과 본문, PR 리뷰 코멘트
- 이슈/PR 템플릿, 라벨 이름과 설명
- 릴리스 노트, changeset 요약

**영어로 바꾸지 않는다:**

- 사용자와의 **대화 응답** — 사용자가 쓰는 언어를 따른다.
- 코드 주석·코드 내 문자열·문서 파일(README 등) — 저장소의 기존 관례를 따른다(주석은 위 "주석 언어").

이슈와 PR은 저장소에 영구히 남아 외부 기여자·미래의 협업자·검색 엔진이 읽는 공개 산출물이라 영어로 통일한다.

- **사용자가 특정 이슈/PR에 대해 언어를 명시적으로 지정한 경우에만** 그 언어로 작성한다. 그 지시는 해당 건에만 적용되고, 다음 건은 다시 영어가 기본이다.
- 저장소의 기존 이슈가 다른 언어로 쌓여 있어도 새 이슈는 영어로 쓴다. 기존 이슈를 일괄 번역하지는 않고, 크게 고쳐 쓸 일이 생기면 그때 영어로 바꾼다.
- 코드 식별자·파일 경로·로그 출력·명령어·에러 메시지는 **번역하지 않고 원문 그대로** 둔다.

### 자기완결적으로 쓴다

이슈·PR 을 읽는 주체는 **이 대화를 전혀 보지 못한 다른 세션(또는 사람)** 이다. 본문은 그것만 읽고도 재현·수정·검증(PR 은 리뷰)까지 갈 수 있어야 한다.

판단 기준 한 줄: **"이 저장소를 처음 보는 사람이 이 본문만 읽고 작업할 수 있는가?"**

- 링크로 때우지 않는다. 다른 이슈·커밋을 참조하더라도 핵심 내용은 본문에 다시 적는다.
- 버그·성능·아키텍처 이슈는 길어도 된다. 근거를 덜어내 짧게 만드는 것은 읽는 쪽의 조사 시간을 늘린다. 반대로 한 줄짜리 오타 수정에 긴 구조를 강요하지 않는다.
- 관련 있지만 별개인 문제는 별도 이슈로 쪼개고 `#123` 으로 상호 참조한다. A만 고치면 B가 드러나는 관계면 그 인과를 적고 같은 PR로 묶으라고 밝힌다.

### 근거는 실측값으로, 확인과 추측을 구분한다

- 실행한 명령은 **출력과 함께** 붙인다. 측정했으면 수치를 표로 넣는다.
- 확인 기준을 한 줄로 남긴다 — 재현·측정한 브랜치와 커밋, 결과에 영향을 주는 도구·런타임 버전. 예: ``Confirmed on `main` at 60532b8, with pnpm 10.29.3:``
- 코드만 보고 추론한 것은 "재현하지 않았다", "Likely cause: …" 처럼 **명시**한다. 읽는 쪽이 어디까지 믿어도 되는지 알 수 있어야 한다.
- 조사 중 의심했다가 정상으로 판명된 것도 적는다. 다음 세션이 같은 곳을 다시 파헤치지 않게 한다.
- 대화 경위("처음엔 ~했다가")는 쓰지 않는다. 검토했다 기각한 대안은 설계 근거이므로 이유와 함께 쓴다(PR 은 `Notes for reviewers`).
- **하지 않은 검증을 체크하거나 통과한 것처럼 적지 않는다.** 템플릿 체크박스는 실제로 한 것만 체크한다.
- 사용자가 "확인했다"고 알려준 것은 그대로 근거가 된다. 다만 사용자가 확인한 범위를 넘겨 적지 않는다.

### 저장소 템플릿 우선

작성 전에 템플릿을 찾는다. 템플릿이 있으면 그 필드와 필수 항목을 따르고, 템플릿이 정한 제목 접두어·라벨도 따른다. 템플릿과 스킬 기본 구성을 어떻게 합치는지는 스킬 `issue`·`pr` 에 있다.

```bash
ls .github/ISSUE_TEMPLATE/ .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE* 2>/dev/null
```

### 제목

- 형식은 `type(scope): summary`(scope 선택, 마침표 없음, gitmoji 없음). 저장소 템플릿이 제목 형식을 정하면 그것이 우선한다.
- 이슈는 해결책이 아니라 **문제나 필요**를 한 줄로 드러낸다. 파일명만("Update iframe.tsx")이나 증상만("broken") 적지 않는다.
- PR 은 **무엇이 어떻게 달라지는지**를 결과로 적는다. 예: `fix(demo): fit the stacked layout and toolbar to a phone width`.

### 생성 도구 문구 금지

- 이슈·PR 의 **본문과 코멘트**에 AI 생성 도구 관련 문단·서명·배지를 넣지 않는다. 예: `🤖 Generated with [Claude Code](https://claude.com/claude-code)`, `Generated by GitHub Copilot`, `Co-authored-by: ...`, "This PR was written by AI"
- 에이전트·스킬·CLI의 기본 동작이나 템플릿이 붙여도 **제출 전에 지운다.** 이 규칙이 그 기본 동작보다 우선한다.
- 제출한 뒤 본문·코멘트에 남아 있지 않은지 확인한다. 확인 명령은 스킬 `pr`·`issue` 의 등록 단계에 있다.
- 이유: 커밋 트레일러 금지와 같다. 영구히 남는 산출물에 작성 도구 정보가 섞이지 않게 한다.
